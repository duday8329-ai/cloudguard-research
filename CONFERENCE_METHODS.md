# Conference Methodology

## Study objective

This study evaluates CloudGuard, an AWS Infrastructure-as-Code analyzer for
Terraform and CloudFormation. CloudGuard parses uploaded configuration text,
tests predefined policy rules, assigns severity, and produces a remediation
recommendation. The research question is whether a common policy-instance
representation can make detection and risk assessment reproducible across two
IaC formats.

## Research questions

* RQ1: How accurately does CloudGuard identify labelled policy violations?
* RQ2: Does policy-instance normalization support comparable evaluation across
  Terraform and CloudFormation?
* RQ3: What processing time does the prototype require on the frozen benchmark?
* RQ4: Can remediation quality and ranking quality be evaluated with retained
  before/after configurations and independently assigned relevance labels?

RQ4 is a planned experiment in this repository. It must not be reported as a
completed result until the required raw artifacts exist.

## Benchmark and unit of analysis

The current frozen benchmark contains 25 Terraform and 25 CloudFormation
manifests generated by `scripts/bootstrap_benchmark.py`. Five policy families
are represented: public S3 access, public RDS access, disabled RDS encryption,
unrestricted security-group ingress, and wildcard IAM actions. Each case is a
controlled positive or negative mutation. The unit of analysis is:

`U = <file_id, resource_id, policy_sid>`

Ground truth is stored in `annotations/consensus.csv`; `expected_violation=1`
means that the policy criterion is violated. Provenance and annotation source
are recorded per row. The current labels were created by the project team using
predefined criteria, not by two independent certified reviewers.

## Detection procedure

1. Freeze the benchmark manifest and tool versions.
2. Run each analyzer without changing the source files.
3. Normalize findings to `file_id, resource_id, policy_sid, violation`.
4. Join normalized predictions with the policy-instance ground truth.
5. Derive TP, FP, FN, TN, precision, recall, F1, FPR, and FNR from the join.

The current CloudGuard run is generated by `scripts/run_cloudguard.py` and
scored by `scripts/calculate_metrics.py`. A perfect score on this controlled
benchmark is expected to be optimistic because the mutations exercise the same
limited rules implemented by the prototype.

## Baseline comparison

Checkov, KICS, and Trivy must be run on the same frozen files. Their raw output,
version, command line, and semantic mapping must be retained before comparison.
Trivy 0.74.0 has been run and its raw JSON is retained, but its findings are
not yet mapped to the five CloudGuard policy SIDs. Checkov and KICS remain
unavailable in the current environment. An unmatched rule is not treated as a
match merely because its wording is similar, so no baseline precision/recall
comparison is reported yet.

## Ranking, remediation, and latency

Ranking requires independently assigned relevance values for each finding and a
stored ordering seed. Report NDCG@10 only from those labels. Remediation requires
the original file, generated patch, syntax validation, re-scan result, gate
outcomes, and failure reason. Report clearance and validation rates only from
those retained cases. Latency is measured by repeated local runs and reported
with sample count, median, p95, machine description, and tool version. The
current package measures CloudGuard latency only; ranking and remediation remain
pending.

## Reproducibility and limitations

`python scripts/reproduce_all.py` regenerates all currently available artifacts.
The repository is a project-team synthetic mutation study and should be
described as such in a submission. Claims about independent human agreement,
production generalization, external baseline superiority, developer studies,
or large benchmark counts require new evidence and must not be inferred from
the current run.
